## Invariants (all phases)

1. **Auto-advance window**: between Phase 3.7 approval and the start of Phase 5's team-lead validation, do NOT ask permission at task or phase boundaries; state the next action in one sentence and execute. Before approval, asking is REQUIRED. From validation onward, asking is CORRECT. Commits, pushes, PR-body updates, and test runs are within standing approval.
2. **Stop only** for the criteria in SPRINT_STOPPING_CRITERIA.md; never for implementation choices, approach uncertainty, or "confirming the next step".
3. **Open-the-file verification**: before reporting any checklist section, phase, or close-out complete, OPEN the governing checklist in the same turn and walk it line by line: `DONE (<evidence>)`, `N/A (<why>)`, or `NOT DONE -> doing it now`. "I believe I did that" is not verification.
4. **User-request inventory**: a message with multiple asks is a CHECKLIST, not a theme. Enumerate every discrete ask before starting; restate each with its status before ending the turn. A terminal condition ("continue until X") is itself an ask.
   - **A repeated instruction means MY READING is wrong, not the instruction.** If the team lead issues an instruction I believe I have already satisfied, do not execute the same interpretation again. State the reading back in one sentence and act on the other plausible reading.
5. **Read the format doc before producing its output**: retrospective template, backlog presentation format, plan template. Mirror exactly; never reproduce from memory.
6. **Decision-Class Checkpoint Protocol**: sprint-plan approval is NOT authorization for (Class 1) design-decision changes -- anything amending an ACCEPTED ADR's spine (record classes, contexts, certainty model); (Class 2) evidence-claim changes -- asserting a certainty level or fidelity higher than a record's provenance supports; (Class 3) scope changes -- de-scoping or deferring approved work. STOP, surface with the template phrasing ("This would change ...: [what]. Should I proceed?"), WAIT. Anti-pattern signals: "it is just a small change", "I will mention it in the retrospective", "we are running out of time, I will defer Z".
7. **VERIFY BEFORE AMENDING.** A review finding -- internal or external, from a person or a model -- is NOT actionable until independently verified against the code or the artifact it describes. Corrections to an ACCEPTED ADR are recorded as dated amendments at the bottom, never as edits in place (CLAUDE.md "Early innovation: expect revision").
   - Corollary: **correcting a document does not correct its generator.** When an amendment corrects a claim, check the code that produces that claim's evidence, not only the prose stating it.
8. **If Phase 1 was skipped for a sprint, STOP and return to it** before any Phase 4 work.

## Phase detail (adaptations from the source; consult spamfilter's doc for rationale history)

### Phase 1: Backlog Refinement (Sprint N's first phase, on Sprint N's branch)
**Re-homed 2026-09-19 (Sprint 4 Task A, team lead).** Until then this document carried Backlog Refinement twice -- here as "Phase 1, every sprint" AND under "Phase 8: Delivery Cycle" of the prior sprint -- and other repositories run it as an early phase of the NEXT sprint's branch. The double homing meant a session spent the delivery cycle reporting the old sprint's number on the new sprint's branch, and the close-out Stop hook and the sprint_status guard test contradicted each other for exactly those turns (F27). One numbering now: **a sprint is called by its branch number from the 6.6 carry-forward cut onward.** `sprint_status.json` advances to N at the cut with `status: "Phase 1.1 Backlog Refinement"` (the footer's "Phase n.n Name" format, Sprint 7 retrospective I6) and `plan_doc: null`; the guard test requires a plan document only from Phase 3.
- 1.1 **CHANGELOG reconciliation for Sprint N-1, before the sweep** -- detail under "Phase 1 detail" below.
- 1.2 **Refinement Pass 1, completeness sweep for Sprint N-1**: issues closed, docs triad present (write `SPRINT_{N-1}_SUMMARY.md` here if Phase 7 did not), master plan rolled (Last Completed Sprint, Past Sprint Summary row) and shipped cards pruned BY HAND, `sprint_status.json` current. Corrections only; NEVER selects scope.
- 1.3 **Design-document currency check** -- ADR-0004/0005 still match the actual schema and the store. **The probes (F53) are not re-run each cycle** (team lead, 2026-10-09; ADR-0005 A6 (c)): a record is re-checked about 12 months after its last check, a brief check of one arXiv request per paper, on the staggered schedule F64 built (ADR-0005 A7, Sprint 8). **Phase 1.3 runs `python scripts/probe_reference_fields.py --due --apply --sessions --progress <file> --report <file>`**: only the papers whose computed next re-check date has passed (about 1/24 of the store per two weeks, nothing before mid-August 2027), every kind of paper, ending with three lists for the team lead (re-pull, withdrawn, newly published) plus local copies missing or changed; nothing is downloaded. `view.py paper <id>` shows a paper's section and next date. A full refresh, if ever needed, is `python scripts/probe_reference_fields.py --refresh --apply --sessions --progress <file> --heartbeat <file>` inside F52's arXiv cap (measured at Sprint 7 Task C: 1,524 records took 36 hours in API mode; ADR-0005 A6 (d)).
- 1.4 **Refinement Pass 2, scope selection**: read ALL_SPRINTS_MASTER_PLAN.md and repo-root CHECKLIST-Phase2-pre.md; identify stale/obsolete items; re-prioritize; present "Sprint N Candidates at a glance" in the BACKLOG_REFINEMENT.md "Backlog Presentation Format" -- Summary Index first, `**<ID>. <Title> (~<effort>) Priority <N>**` items, phase-group headers, HOLD one-liners, no grid tables, real registered IDs. Read the format section in the same turn before producing it.
- 1.5 Record selection; update master plan; commit; proceed to Phase 2.

### Phase 2: Sprint Pre-Kickoff
- 2.2 Previous sprint PR merged to develop (`git log origin/develop --oneline -1`). Branch retention: NEVER delete sprint branches, local or remote.
- 2.3 Previous sprint's GitHub issues all closed (`gh issue list --label sprint --state open`); since 2026-10-13 develop is the repository default (F66, ADR-0001 A2), so `Closes #N` in a PR body or commit message closes the issue when the PR merges into develop. Before that date it did not fire on feature->develop merges. Still run the command and close any issue left open by hand: an issue named without `Closes` stays open.
- 2.4 Working tree clean. 2.5 develop current.
- 2.6 Dependency check: `uv pip list --outdated` scan; security-relevant bumps become scope or backlog items.

### Phase 3: Kickoff & Planning
- 3.2.1 **Three-doc rule, no exceptions**: every completed sprint has SPRINT_N_PLAN.md, SPRINT_N_RETROSPECTIVE.md, AND SPRINT_N_SUMMARY.md. The summary is created at Phase 7 (as Sprints 2 and 3 did) or at the latest in Sprint N+1's Phase 1.2 sweep (sources: retrospective, git history, PR; never the already-rolled master plan) and its absence blocks Sprint N+1's Phase 3. **The summary carries an `## Actuals` section** (Sprint 3 retrospective improvement 2): per task, wall-clock from the previous task's commit to this task's commit (derived from `git log`, not remembered), and for any delegated subagent its reported tokens and duration. Three sprints ran with every estimate `[no-history]` because actuals were never written down in a form the next plan could read; SPRINT_PLANNING.md's "record actuals at task completion" was a rule with no artifact behind it.
- 3.2.2 Plan doc with objective, tasks, acceptance criteria (quantifiable), risk, estimates in MINUTES.
- 3.2.2.1 **Plan-to-branch-state verification**: before committing the plan, verify each task against the repo (artifact exists? already shipped? cited paths current?). 3.2.2.2 Re-estimate after findings.
- 3.3 Branch `feature/YYYYMMDD_Sprint_N` -- normally ALREADY CREATED by the previous sprint's 6.6 carry-forward; verify, do not duplicate.
- 3.3.1 **Draft PR immediately after the plan is drafted, before approval. The PR STAYS DRAFT through Phase 7.7.** Draft status suppresses Copilot per-commit reviews; marking ready early = review noise on every push. `gh pr ready` happens at exactly one place: end of 7.7.
- 3.4 One GitHub issue per task (`sprint` label), created in the SAME turn as approval acknowledgment, before any task file is touched. 3.4.1 Verify each issue is still real. 3.5 All cards OPEN.
- 3.7 Explicit approval; update PR body to approved plan (keep draft).
  - **The plan absorbs its decisions in the commit that records them** (Sprint 7 retrospective I2, 2026-10-09). Every task line a decision changed is rewritten there: its runtime recomputed from the chosen option (SPRINT_PLANNING.md, "Every option in a decision states its cost") and its acceptance criteria restated. Sprint 7 kept Task C's 5.8-hour runtime after Q5 and Q7 made it 36 hours, and Task B's acceptance still named a "full export" and a "committed fixture" after Q1 = 2 removed both; the acceptance walk then had to explain the difference instead of checking it.

### Phase 4: Execution
- Tasks in plan order; `pytest -q` after each change; commit referencing the issue (`#N`).
- **A commit gated on tests is gated on the TEST RUNNER'S exit code, never on a pipeline's last command** (Sprint 4 improvement 1). `pytest -q | tail -1 && git commit` commits a red suite, because `tail` succeeds; it happened on 2026-09-20 and put two ADR amendments in with one test failing. Use `pytest -q > /tmp/suite.txt 2>&1; rc=$?; tail -1 /tmp/suite.txt` then `test $rc -eq 0 && git commit ...`, or drop the pipe entirely. Hook-enforced: `.claude/hooks/block_commit_with_piped_tests.py`.
- **More than one session may be working the same branch. Fetch before each task and read the other session's note** (Sprint 4 improvement 4). `git fetch origin` and read `origin/<branch>:.claude/sprint_status.json`'s `note` field before starting a task, so work already done elsewhere is not repeated and a blocked task is picked up deliberately. A REJECTED PUSH means the same thing and is handled the same way: fetch, read the note, read the commits, then rebase; it is not a git problem to be forced past. In Sprint 4 a remote session completed four tasks and recorded a Criterion 2 block on a fifth, and this session discovered all of it only when its push was rejected. The `note` field is the hand-off channel between sessions; it is written at every task boundary and read at every task start.
  - **The note written at a task's start carries the clock time** ("2026-10-08 09:55: F started"; Sprint 7 retrospective I7, 2026-10-09), so the summary's `## Actuals` measures each task from its start, not from the previous task's commit. Sprints 6 and 7 both recorded that work done before a commit made commit-to-commit actuals a lower bound only.
- `git status --short` before every staging; account for every entry. Team-lead working files (`0*` at root) are EXPECTED to change and be committed with a neutral message; never read, paraphrase, or exclude them.
- Provenance discipline: every record's `provenance` field is set before the record is committed; a record that cannot say where its value came from is the defect this whole system exists against (CLAUDE.md).
- **A delegated task's report is verified against repository state before it is trusted OR dismissed** (Sprint 3 retrospective improvement 3). Check `git log`, the files it names, and the issue it closes; a subagent or fork cannot commit under this session's identity, so a claimed commit either exists or the report is wrong. In Sprint 3 a fork's accurate completion report was briefly distrusted after a context compaction hid the turn in which its work had been committed -- the fix was `git show <hash>`, not a judgment about the messenger.
- **Write-shaped one-off scripts run dry by default** (Sprint 3 retrospective improvement 1; convention in QUALITY_STANDARDS.md). Show the diff or the planned change list first; write only on an explicit `--apply`. Review the dry-run output against the frozen-document rules (ADR amendments, sprint docs) before applying.
- **A finding that a paper has no local copy is computed, never asserted by hand** (Sprint 8 retrospective I2, 2026-10-13). Search the whole collection with `store.recheck.local_copies(<id>)`, which also completes a new-style id one digit short, before a report or a decision question says a file is absent. Sprint 8's F60 report said the Asfaw paper was never downloaded, after searching only its row's folder; it was in `Workforce`, and the team lead was asked to approve a download that was not needed.

### Phase 5: Review & Validation
- **Before declaring Manual Validation ready, run `gh issue list --label sprint --state open` and account for every result.** Added 2026-09-17 (Sprint 2 retrospective improvement 1) after issues #13 and #15 stayed open despite `Closes #N`-style commit messages referencing them on the feature branch -- `Closes #N` fires only on a merge into the repository's default branch, which was main until 2026-10-13, a gap this document already named (2.3) before it recurred anyway. Since develop became the default (F66, ADR-0001 A2), a feature->develop merge closes the issues its `Closes #N` lines name; this check stays as the backstop for an issue named without `Closes`, and for an issue checked before its PR merges. Documenting a gap is not the same as checking for it; this step makes the check mechanical rather than triggered only if the team lead happens to ask.
- Full test suite, run locally so the `live_store` tests run: they check the REAL data in the store outside the repository, and a missing store fails them (ADR-0004 A7, 2026-10-06; until then this step compared the committed export with a fresh regeneration, `tests/test_export_currency.py`, retired with the export).
- **Evidence-generating steps invalidate their own verification.** Any checklist walk, memo, or summary is generated AFTER the last piece of evidence lands, never before. A verification artifact written mid-task is stale by construction and must be regenerated, not referenced.
- **Fresh-eyes review before a major structural change lands** (schema, contexts, resolvers): a fresh-context reviewer (subagent or fresh session with no task context) reads the raw change with an open prompt ("describe; any useful observations?"); findings attach to the validation package. The invested session knows what a change is supposed to mean; fresh context describes what it actually does.
  - **When: at the task's commit, in Phase 4, not batched into Phase 5** (Sprint 5 retrospective improvement 5, 2026-09-25). Sprint 5's durability code (Task A) was reviewed only at Phase 5; by then it had taken nine backups before real writes, and the review found four defects, including a restore that could not restore a corrupt store. Any task that adds or changes store/, a hook, a resolver, or a recovery path gets its reviewer launched in the background as soon as it commits, while the next task proceeds; the Phase 5 review then covers only what changed since.
- Walk the sprint plan's acceptance criteria line by line with evidence (invariant 3).
- **Re-read every ADR amendment written this sprint against the code** (Sprint 6 retrospective I4, 2026-10-05). Each sentence that names a script, a table or a behavior is checked against what the branch actually contains; what was not built is stated as not built, in the amendment, before it reaches Manual Validation. Sprint 6's ADR-0005 A4 said `refresh_citations.py` re-runs the probes each Phase 1.3 and reports stale ones; neither existed, and it was caught only because the Phase 5 evidence pass happened to read that paragraph. Amendments are written ADR-first, before the code, so they describe intent; this step turns intent back into fact.
  - **The re-read covers every document that restates the amendment** (Sprint 7 retrospective I5, 2026-10-09). Search `CLAUDE.md` and `docs/` for each amendment's key terms (the script, the setting, the path, the behavior) and correct each restatement that disagrees, in the same commit. Sprint 7's I4 re-read corrected ADR-0004 A7 (e) to "deselects them by their marker", while `CLAUDE.md` kept "CI deselects them by name" into the retrospective.
- Hand deliverables to the team lead for manual validation; from here on, questions are correct.
  - **Every decision question in the hand-over ends with a "Recommend N" line, and a question with numbered options is titled as a choice, never as yes/no** (Sprint 8 retrospective I1, 2026-10-13; CLAUDE.md "Things Claude Should NOT Do"). Sprint 8's Q5 ("Should the 7 past release merges be tagged too?") drew a "yes" that had to be interpreted, and Q7 had no recommendation, so "as recommended" bound to nothing and Q7 was asked again.
- **What Manual Validation is, and is not** (team lead, 2026-09-19, Sprint 4): everything that reaches the team lead has no errors remaining -- development tests, unit tests, integration tests, CI and Claude's own analysis of the results have resolved them before hand-over. Manual Validation is for exercising functionality delivered to end users or customers, and for decisions only the team lead can make. A test run, a dry run, a byte-identity check or a data spot-check is never a Manual Validation step; state in one line that they passed. **An amendment to an existing ADR is presented for review as `ADR-<n> <adr-name>`, then What changed and Why, then the specific language to be reviewed, quoted** -- the team lead reviews text, not a pointer to a file. ADR reviews come first, then the functional steps.

### Phase 6: Push & Finalize PR
- 6.3 Update the existing draft PR (never create a second). 6.5 interim status to the team lead, NOT "ready".
- 6.6 **Carry-forward**: on merge notification, immediately `git checkout -b feature/<date>_Sprint_<N+1>` FROM the current feature branch; commit post-merge work there; push. NEVER stash to carry forward; never branch from develop after the merge (loses uncommitted work; the recovery is cherry-pick onto a develop-cut branch and reset the merged branch to its pushed head).
  - **Both clauses are hook-enforced** (`.claude/hooks/`): `block_carry_forward_stash.py` blocks `git stash`, `block_branch_from_develop.py` blocks a `checkout -b`/`switch -c` that names develop, main or master as the start point. Bare `git checkout -b <name>` is the prescribed form and passes; both hooks carry a sanctioned bypass token for the genuine exception. (Converted from `.ps1` to `.py` 2026-09-14; see QUALITY_STANDARDS.md amendment.)
  - **A clean result does not mean the cut was right.** At the Sprint 9 close-out the branch was cut from `origin/develop`; no commits were lost, because the merge had already carried everything and the uncommitted work followed the checkout. The violation was invisible in `git status` and surfaced only on re-reading this rule. Verify the flow, not the outcome.

### Phase 7: Retrospective (mandatory before merge-ready)
- Follow SPRINT_RETROSPECTIVE.md's 7-step protocol: prompt to team lead -> Claude drafts its role's feedback in parallel (`docs/sprints/drafts/`) -> record team lead's words verbatim -> combine and display -> propose improvements (Title/Source/Type/Effort/Recommendation) -> team lead disposes each (now/backlog/skip) -> apply now-items as commits, backlog-items to master plan.
- Exit gate: 16 categories x 4 roles, no placeholders; Category 13 feeds Sprint N+1's plan; Category 14 feeds the master plan.
- **Merge-readiness definition (team lead, 2026-09-04)**: a PR is handed to the team lead as merge-ready ONLY when EVERY review has COMPLETED and EVERY finding is addressed and its thread resolved. A review still running means the PR is not ready, no matter how clean it looks; never describe it as "yours to merge" while an agent is mid-review. State review status explicitly instead: which reviews are complete, which are running, how many findings are open.
- End of 7.7: `gh pr ready` (the only place). 7.7.5 final gate: manual validation + retro + improvements + Copilot review all complete -> notify team lead for final approval.
- **Requesting the Copilot review (CORRECTED 2026-09-12, F66).** This has three independent silent-failure modes, and the earlier note in this document recorded the workaround while misdiagnosing the cause.
  - **The actor name is `copilot-pull-request-reviewer[bot]`** (node id `BOT_kgDOCnlnWA`). NOT `Copilot`, and NOT `copilot-swe-agent`, which is a different bot. `gh pr edit --add-reviewer Copilot` reports success and attaches nothing, because it resolves a user named Copilot that does not exist on the repository.
  - **`requestedReviewers` cannot confirm a bot request.** The REST field returns USERS only, so a bot reviewer that attached correctly still reads back as an empty list. Verifying there produces a false negative every time, which is what made the first failure mode look like a second one.
  - **Verify on the TIMELINE instead**: the PR shows "Copilot started reviewing" / "Copilot reviewed", or `gh pr view <N> --comments` shows the review body. That is the only reliable confirmation.
  - **Consequence, recorded because it actually happened**: PR #73 never received a Copilot review. The request was issued, reported as successful, verified against a field that cannot show it, and nobody noticed until PR #75 was being set up. A review step that silently does not happen is worse than one that visibly fails.
  - **The working request path, verified 2026-09-14 on PR #94**: the GraphQL `requestReviews` mutation with the bot id in `botIds`, NOT `userIds`. `userIds` fails loudly with "Could not resolve to User node", which is at least honest. **The REST call fails SILENTLY**: `POST /pulls/{n}/requested_reviewers` with the bot login returns HTTP 200 and a full PR object, and attaches nothing. That is a fourth silent-failure mode beyond the three already listed.
    ```
    gh api graphql -f query='mutation($pr:ID!){requestReviews(input:{pullRequestId:$pr, botIds:["BOT_kgDOCnlnWA"], union:true}){pullRequest{number}}}' -f pr="<PR node id>"
    ```
  - **Verify with GraphQL `reviewRequests`, never REST.** REST's `requested_reviewers` showed an EMPTY array while GraphQL showed `Bot: copilot-pull-request-reviewer` attached. The timeline also showed no `review_requested` event for the bot, so the timeline check in the line above is necessary but NOT sufficient. A cross-repository skill holds the full procedure; this note exists so the workflow does not depend on that skill being loaded.
- Update `.claude/sprint_status.json` `current_sprint.status` at every phase transition (it is how future tooling knows which side of the auto-advance window applies). **One format: "Phase n.n Name -- detail"** (for example "Phase 4.1 Execution -- Task C next"; Sprint 7 retrospective I6, 2026-10-10). The status footer reads the phase from it, and the Phase 4 Stop hook and `tests/test_sprint_documents.py` read the phase number from it; a test fails on any other form. The file carries no `updated` date: `git log` answers when it changed.

### Phase 8: Delivery hand-off (the finishing sprint's last phase)
- 8.1 Team lead merges feature -> develop (on the 7.7 ready notification), then develop -> main. Claude never merges.
  - **The release step** (F66, ADR-0001 A2, 2026-10-13): PR develop -> main, merged by the owner, then tag the merge. The tag is `sprint-N`, an annotated tag on main's merge commit, message `Sprint N release: develop merged to main by PR #M`; Claude creates and pushes it on the main-merge notification (`git fetch origin`, `git tag -a sprint-N <merge commit> -m ...`, `git push origin sprint-N`). Tags `sprint-1` to `sprint-7` were added on 2026-10-13 for the earlier releases.
- 8.2 On the develop-merge notification, the 6.6 carry-forward cut: `git checkout -b feature/<date>_Sprint_<N+1>` FROM the current feature branch. **The moment that branch exists, Sprint N is over and the session is in Sprint N+1 Phase 1.** In the same turn: advance `sprint_status.json` (`current_sprint` = N+1, `status: "Phase 1.1 Backlog Refinement"` (the footer's "Phase n.n Name" format, Sprint 7 retrospective I6), `plan_doc: null`, `pr: null`, `plan_approved: false`, `github_issues: []`; `last_completed_sprint` = N with `merged_pr`, and `main_merge_pr` once known), and the status line reads "Sprint N+1 Phase 1.x". Everything that used to be listed here as 8.1.1-8.4 is Sprint N+1's Phase 1.1-1.4; the detail follows.

### Phase 1 detail (formerly Phase 8.1.1-8.4, re-homed 2026-09-19)
- 1.1 **CHANGELOG reconciliation, BEFORE refinement (F70, Sprint 14).** Walk the days since the last entry and write one per day with commits, sourced from git history, the sprint summaries, the amendment log and the merged PRs. A day that cannot be reconstructed with confidence says so rather than being invented.
  - **Why this step exists and why it sits here.** The policy at the top of CHANGELOG.md says entries are written in the SAME commit as the change they describe. That policy held for six days and then silently stopped: the file ran from 2026-08-29 to 2026-09-04 and then nothing, while Sprints 7 through 13 delivered the entire hardware campaign, three external reviews, the public-repository flip and the submission itself. Eight days missing, and nobody noticed for eight days.
  - A same-commit policy depends on remembering at the moment of committing, which is exactly the class of rule this workflow keeps having to replace with a step. The reconciliation is cheap when it runs every cycle and expensive once it has lapsed -- the F70 backfill cost about ninety minutes for eight days.
  - It is placed BEFORE Refinement Pass 1 deliberately: the sweep reads the sprint's own record, and a record with a hole in it is what the sweep is meant to catch.
